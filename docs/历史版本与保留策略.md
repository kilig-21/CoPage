# 历史版本与保留策略

第一阶段支持历史列表、富文本预览、所有者恢复及重要版本标记。恢复产生新 revision，通过同一协同提交链路持久化和广播；预期版本校验防止覆盖并发编辑，请求 ID 防止超时重试重复恢复。

## 如何控制容量

每次编辑保存增量操作，通常每 20 个版本产生周期快照；读取历史时从最近快照连续重放操作，不是每敲一个字都保存整篇正文。恢复整篇旧内容的操作可能较大，单个操作限制 4 MiB，当前 Delta 正文限制 2 MiB。

普通历史默认按 30 天、10000 次操作、64 MiB 逻辑内容取更严格的保留范围。容量统计包含操作、快照和收据，为新基准快照预留正文空间。重要版本保存独立完整正文，每篇最多 20 个、总正文最多 32 MiB；达到上限时先取消旧标记。当前正文不受历史清理影响。

64 MiB 是普通历史的逻辑内容目标，不是 MySQL 数据文件的硬上限。索引、数据库页、事务日志、图片和当前正文另占空间；文档数量增长仍会增加总容量。自动任务分批检查，每轮最多 50 篇活跃文档，默认每小时一次，因此清理存在延迟。InnoDB 删除后通常复用空闲页，不保证数据文件立即变小。

## 清理与启用

**自动清理默认关闭**，待负责人决定是否接受旧普通版本不可恢复后再开启。所有者可先从历史抽屉查看清理范围，手动点击“清理过期历史”并确认。清理在文档锁和数据库事务内保存起点基准、裁剪旧日志/收据并推进起点，不改当前正文和 revision。清理之后，起点仍可查看；更早的普通版本不可恢复，已标记的重要版本继续可读、可恢复。

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `HISTORY_RETENTION_ENABLED` | `false` | 是否自动清理 |
| `HISTORY_RETENTION_DAYS` | `30` | 普通历史保留天数，至少 1 |
| `HISTORY_MAX_OPERATIONS` | `10000` | 连续操作数量，至少 2000 |
| `HISTORY_MAX_BYTES` | `67108864` | 普通历史逻辑字节目标，至少 4 MiB |
| `HISTORY_PROTECTED_DOC_IDS` | `26` | 逗号分隔的受保护文档 ID |

本机 Java 进程启动前设置环境变量；Docker Compose 从项目 `.env` 或启动 shell 读取。修改后需要重启对应后端；容器可执行 `docker compose --profile app up -d --no-deps backend`。前端通常连接 8080，8082 容器不会自动替代它，两个实例应使用一致策略。不要移除文档 26 的保护，也不要删除它或 testB 编辑权限。

软删除超过保留天数的文档也可压缩普通历史，保留当前正文、文档行、单个基准快照和重要版本；软删除不是彻底擦除，也不自动清理 MinIO 图片。

## 断线恢复边界

2000 条以内的完整历史随同步消息返回，更长历史按固定目标版本分页，每批最多 256 条，普通页约 1 MiB，较大的单个合法操作可单独返回。客户端先在工作副本上验证连续历史并进行 OT，全部完成后再一次性更新正文和待确认队列；确认丢失的自身操作不会重复应用。

历史已超出保留起点或日志有缺口时，系统保留本地草稿并停止自动合并，不把服务器快照强行覆盖到未确认内容上。此时先复制备份，再人工处理。收据裁剪后拒绝过旧请求基线，防止重复编辑。

## 验收依据

后端 85 项、前端 24 项测试及构建通过。真实 2005 次远端编辑的两种断线场景均分 8 页恢复，正文收敛；10050 操作验证数量/年龄清理，约 100 MiB 合成快照验证容量裁剪后逻辑内容为 66058123 字节。20 个重要版本及第 21 个被拒绝、基准可读、旧版本拒绝、重要版本跨清理保留、过旧操作不能重复提交均已验证。自动维护的开关、保护文档和软删除锁路径有单测；真实数据库压缩由手动接口烟测验证，不记作自动任务运行验收。
