## 架构问题的准确口径

- **为什么需要 OT？** 两个客户端的操作可能基于同一旧版本。服务端用已提交的历史操作转换后到的操作，分配唯一递增 revision；客户端把远端操作与本地 pending/buffer 重新对齐。固定用例与 1 万组 TP1 随机用例验证核心转换性质，但不能因此声称覆盖所有真实浏览器组合。
- **为什么有 Redis 锁、MySQL、RabbitMQ？** Redis 锁保护同一文档的提交顺序，Pub/Sub 把已提交操作送到其他实例；MySQL 是持久化事实来源。**RabbitMQ 不承担当前版本的异步正文落库**，而是接收已提交操作的通知，驱动快照与搜索索引的后续处理。早期方案中的“MQ 异步批量落库”已经不是当前实现，不应作为答辩亮点。
- **崩溃后怎么恢复？** 以 MySQL 中同一版本的正文和 revision 为基线，从操作日志追赶；Redis 热状态可重建。opId 收据可识别“已提交但 ACK 丢失”，避免重复应用。连续历史超过单次2000条且仍在保留范围内时，按固定目标分页追赶，每页最多256条；先验证并处理工作副本，再一次性更新正文和未确认队列。历史缺失或早于保留起点时，保留草稿并停止自动合并。2005次远端编辑的两类pending场景已有8页恢复记录，不能推广为所有日志缺失都能恢复。
- **四类中间件的真实职责？** Redis 负责锁、热状态、在线状态与跨实例广播；RabbitMQ 负责已提交操作后的快照/索引通知；Elasticsearch 是可重建的检索副本，权限仍由 MySQL 判定；MinIO 存图片对象，浏览器地址需单独配置。

## 主动说明的边界

原方案要求“两位不同账号同时编辑、看见彩色光标和名字、刷新不丢”。当前已验证多人操作收敛、刷新持久化、presence，以及 testA/testB 双账号的实时编辑、不同昵称/颜色的远端光标、失焦/离开隐藏和真实后端断线后的恢复；本地浏览器验收记录见[实施计划](实施计划.md)。2026-10-03 已补齐协作者管理、真实搜索和图片按钮上传/实时广播/刷新保留的联合验收。CODI-90 的无刷新自动重连和断线只读已于 2026-10-01 验收，CODI-92 按本地交付范围完成。公网部署可选且尚未执行；RAG 只做演进预留，当前没有 AI 问答功能。超过2000条的连续、保留范围内历史可分页恢复；日志缺失或超过保留起点时仍须备份并人工处理。真实系统输入法尚未实际验收，不把合成事件说成系统输入法操作。
