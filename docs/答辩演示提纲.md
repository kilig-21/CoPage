## 架构问题的准确口径

- **为什么需要 OT？** 两个客户端的操作可能基于同一旧版本。服务端用已提交的历史操作转换后到的操作，分配唯一递增 revision；客户端把远端操作与本地 pending/buffer 重新对齐。固定用例与 1 万组 TP1 随机用例验证核心转换性质，但不能因此声称覆盖所有真实浏览器组合。
- **为什么有 Redis 锁、MySQL、RabbitMQ？** Redis 锁保护同一文档的提交顺序，Pub/Sub 把已提交操作送到其他实例；MySQL 是持久化事实来源。**RabbitMQ 不承担当前版本的异步正文落库**，而是接收已提交操作的通知，驱动快照与搜索索引的后续处理。早期方案中的“MQ 异步批量落库”已经不是当前实现，不应作为答辩亮点。
- **崩溃后怎么恢复？** 以 MySQL 中同一版本的正文和 revision 为基线，从操作日志追赶；Redis 热状态可重建。opId 收据可识别“已提交但 ACK 丢失”，避免重复应用。历史缺失或超出单次 2000 条的场景当前**不是自动合并完成**，用户需先备份本地草稿。
- **四类中间件的真实职责？** Redis 负责锁、热状态、在线状态与跨实例广播；RabbitMQ 负责已提交操作后的快照/索引通知；Elasticsearch 是可重建的检索副本，权限仍由 MySQL 判定；MinIO 存图片对象，浏览器地址需单独配置。

## 主动说明的边界

原方案要求“两位不同账号同时编辑、看见彩色光标和名字、刷新不丢”。当前已验证多人操作收敛、刷新持久化、presence，以及 testA/testB 双账号的实时编辑、不同昵称/颜色的远端光标、失焦/离开隐藏和真实后端断线后的恢复；本地浏览器验收记录见[实施计划](实施计划.md)。协作者管理入口、搜索页接线未完成。图片按钮的浏览器上传/刷新保留和两个已连接标签页之间图片 Delta 的实时广播已分别验证，尚未把二者合并为同一次按钮操作的端到端证明。CODI-90 等待人工复核；CODI-91 的 Vercel/公网后端联调已延期，不能展示为已上线产品。
