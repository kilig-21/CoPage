# 数据库设计

新库初始化源为 [schema.sql](../backend/src/main/resources/db/schema.sql)；既有库由对应Repository执行保留数据的增量迁移。小组DDL集中在[groups.sql](../backend/src/main/resources/db/groups.sql)，新库初始化同步包含同一结构。本地演示数据独立放在 [demo-users.sql](../backend/src/main/resources/db/demo-users.sql)，服务器配置不挂载演示种子。本文件解释字段约束，避免多人各自修改 SQL。

| 表 | 职责 | 关键约束 |
| --- | --- | --- |
| `user` | 账号资料 | `username` 唯一；密码只存 BCrypt 哈希；`credential_version` 非空、默认0 |
| `document` | 当前文档状态 | `content` 与 `revision` 必须用同一条 UPDATE 原子更新 |
| `doc_operation` | 保留范围内的增量日志 | `(doc_id, revision)` 唯一，防止重复提交；清理后不再是永久全量审计 |
| `doc_operation_receipt` | 操作去重收据 | 文档/用户/clientId/opId 联合主键；保存请求指纹 |
| `doc_snapshot` | 定期快照 | 按 `(doc_id, revision)` 查询恢复基线 |
| `doc_collaborator` | 协作者权限 | `(doc_id, user_id)` 唯一；1 只读，2 可编辑 |
| `doc_history_boundary` | 连续历史保留起点 | 每篇文档一行；清理前须有对应的完整基准快照 |
| `doc_named_version` | 用户标记的重要版本 | `(doc_id, revision)` 主键；正文独立保存，每篇最多 20 个、总正文最多 32 MiB |
| `copage_group` | 小组资料与归档 | owner_id绑定可信创建者，name最多80，归档不删除原文档 |
| `group_member` | 独立小组成员 | (group_id,user_id)主键；owner/admin/member；创建者保护 |
| `group_invitation` | 站内邀请与决定 | (group_id,user_id)主键；状态及递增invitation_version阻止旧请求作用于新邀请 |
| `copage_project` | 个人/小组分类资料 | group_id创建后不变；归档保留关联 |
| `project_document` | 项目与原文档引用 | (project_id,doc_id)主键；association_id UUID保护关联代次 |
| `personal_template_owner` | 私人模板配额锁锚点 | user_id主键；写事务先取得排他锁 |
| `personal_template` | 本人独立模板正文与资料 | 正文一次保存；source_revision/version、UTF-8逻辑容量 |

`document.content` 保存 Quill Delta JSON，空文档必须为 `{"ops":[{"insert":"\n"}]}`。Redis 只保留热数据与近端操作历史；MySQL 才是持久化事实来源。

每次协同提交在同一 MySQL 事务中更新 `document.content`/`revision` 并写入 `doc_operation`；确认消息只能在事务成功后发出。Redis 热状态丢失时，直接由 `document` 行恢复内容和 revision，落后操作的 OT 变换从 MySQL 操作日志读取。升级前仅保存在 Redis 的版本会按连续操作日志补入 MySQL；若历史有缺口则拒绝覆盖。

RabbitMQ 接收已落库操作通知，每 20 个 revision 触发 `doc_snapshot` 快照。多实例消费通过锁住文档行实现幂等；定时巡检补发“事务已提交、消息未发出”窗口遗漏的快照任务。快照用于后续历史恢复/审计，不取代 `document` 当前状态的事实来源。

Elasticsearch 的 `collab_documents` 索引是可重建副本，只索引标题和 Delta 的文本插入，不索引图片地址。新建、改名、删除在 MySQL 事务提交后更新索引；协同编辑通过 RabbitMQ 操作通知更新，周期巡检补建漏更新项。搜索前必须先从 MySQL 获取当前用户可见的文档 ID，再以 ES `ids` 条件限制结果，不能把 ES 中的字段当成权限来源。

历史压缩持 Redis 文档锁，在同一事务内写入保留起点的完整快照、删除更早快照及截至起点的操作/收据、更新 `doc_history_boundary`。当前正文与 revision 不变，命名版本独立保留。已清理收据对应的过旧基线被拒绝，避免当成新操作重复提交；仍保留的收据优先用于幂等确认。自动维护默认关闭，文档 26 受保护；软删除超过保留天数的文档可压缩普通历史，但不删除文档行、正文或重要版本。容量统计为逻辑内容，不包含索引、数据库页和 binlog，详见[保留策略](历史版本与保留策略.md)。

账号凭据版本与密码在本人账号行锁及同一事务内更新，用于使改密前的JWT和WS连接失效。既有库由AccountRepository启动时仅补缺失的credential_version BIGINT NOT NULL DEFAULT 0列，多实例竞争DDL后重新检查；不重置账号或密码。该字段纳入SQL备份，恢复后已撤销令牌仍拒绝。新库直接由schema.sql创建。

## 小组增量数据

GroupRepository启动安全建缺表并仅补缺失invitation_version BIGINT NOT NULL DEFAULT 1列，DDL竞争失败后重新核对。新建小组和创建者成员在同一事务保存；组织写操作先锁小组行，随后核对当前成员/角色、容量和邀请版本，避免接受、移除和角色变更并发旁路权限。每组成员与待接受邀请合计200以内，列表分页。

邀请重新发送使用同一group/user记录递增版本，旧接受/拒绝/取消不能改新邀请；同一pending重复发送不改版本。归档保留成员并取消pending，恢复只恢复原成员关系。独立doc_collaborator、document及协同revision不被组织操作修改，组管理员不自动有任何文档阅读或写入权限。新表纳入全库SQL备份；2026-10-09当前源码生产与新卷隔离恢复已完成，七表逐行资料及恢复后角色/权限/邀请代次均通过，详见交付验收清单。


## 项目增量数据

[copage项目DDL](../backend/src/main/resources/db/projects.sql)通过ProjectRepository启动CREATE IF NOT EXISTS，新库schema同步。copage_project保存name80/description300/可信owner_id/group_id（0个人）/is_archived及时间，按owner、group及归档索引；group_id与owner_id创建后不变。project_document以(project_id,doc_id)为主键，保存association_id UUID、added_by、create_time及doc_id索引，只引用原资料，不复制正文/快照/权限。归档保留引用，源软删除/撤权后新读取过滤标题与数量。

写操作依小组→项目→原文档锁顺序，先读取不可变归属后等锁可能建立旧的重复读快照，因此跨模块权限必须FOR UPDATE读取当前group_member；关联也当前锁读，避免并发删除误报changed或旧UUID作用于新关联。INSERT IGNORE重复加入不更新UUID；移出精确匹配本次UUID。两表随全库SQL备份；2026-10-09当前源码实际新卷恢复核对项目归属、归档、关联UUID/时间及当前可见计数，恢复后降权、邀请和归档恢复通过，不沿用旧版本验收。


## 私人模板增量数据

DDL见[personal-templates.sql](../backend/src/main/resources/db/personal-templates.sql)，启动可重复建缺表，新库schema同步。personal_template_owner以user_id为PK，作为每个账号写事务的锁锚点；不能用重复INSERT IGNORE共享锁后升级，采用同一ID的原子upsert取得排他锁，再FOR UPDATE读取。保留空锚点不会占用正文配额。

personal_template保存owner_id/name200/description300/category、唯一content MEDIUMTEXT/content_bytes、保存时source_revision、元数据version及时间，按owner/category/update_time索引。正文规范序列化、单份2 MiB，全账号100份和32 MiB逻辑正文；不保存模板全文历史，不存来源docId或继承授权。改资料只增加version，删除释放当前正文配额（不承诺物理数据库文件立即缩小）。使用在原文档流水保存新的独立正文与版本0，来源后续变化不反向同步。Byte计数与实际保存的UTF-8文本一致。

创建先锁owner、当前来源doc/collaborator后再读配额；改资料/删除锁owner再当前模板，使用当前模板锁并校验expectedVersion。元数据版本拒绝旧删除/使用，模板所有者始终是可信登录人；只读来源明确保存独立副本沿用已有副本规则。新两表纳入完整SQL备份；2026-10-09实际源码生产镜像和新卷隔离恢复已核对全部新增组织/模板资料，不沿用旧版本证据。

2026-10-09当前源码生产与冷恢复实核15张必需表，七张组织/模板表逐行SQL（含正文、UTF-8计数、代次和时间）一致；恢复后的私人模板配额、版本拒绝与独立文档/版本0可继续使用。模板锚点和正文必须与账号一起全库备份，不依赖来源文档或外部缓存。此为本机隔离合成数据验证，实际服务器恢复仍待选定环境演练。
