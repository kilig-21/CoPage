# 数据库设计

SQL 建表的唯一执行源为 [schema.sql](../backend/src/main/resources/db/schema.sql)，本地演示数据独立放在 [demo-users.sql](../backend/src/main/resources/db/demo-users.sql)，服务器配置不挂载演示种子。本文件解释字段约束，避免多人各自修改 SQL。

| 表 | 职责 | 关键约束 |
| --- | --- | --- |
| `user` | 账号资料 | `username` 唯一；密码只存 BCrypt 哈希 |
| `document` | 当前文档状态 | `content` 与 `revision` 必须用同一条 UPDATE 原子更新 |
| `doc_operation` | 全量操作审计 | `(doc_id, revision)` 唯一，防止重复提交 |
| `doc_operation_receipt` | 操作去重收据 | 文档/用户/clientId/opId 联合主键；保存请求指纹 |
| `doc_snapshot` | 定期快照 | 按 `(doc_id, revision)` 查询恢复基线 |
| `doc_collaborator` | 协作者权限 | `(doc_id, user_id)` 唯一；1 只读，2 可编辑 |
| `doc_history_boundary` | 连续历史保留起点 | 每篇文档一行；清理前须有对应的完整基准快照 |
| `doc_named_version` | 用户标记的重要版本 | `(doc_id, revision)` 主键；正文独立保存，每篇最多 20 个、总正文最多 32 MiB |

`document.content` 保存 Quill Delta JSON，空文档必须为 `{"ops":[{"insert":"\n"}]}`。Redis 只保留热数据与近端操作历史；MySQL 才是持久化事实来源。

每次协同提交在同一 MySQL 事务中更新 `document.content`/`revision` 并写入 `doc_operation`；确认消息只能在事务成功后发出。Redis 热状态丢失时，直接由 `document` 行恢复内容和 revision，落后操作的 OT 变换从 MySQL 操作日志读取。升级前仅保存在 Redis 的版本会按连续操作日志补入 MySQL；若历史有缺口则拒绝覆盖。

RabbitMQ 接收已落库操作通知，每 20 个 revision 触发 `doc_snapshot` 快照。多实例消费通过锁住文档行实现幂等；定时巡检补发“事务已提交、消息未发出”窗口遗漏的快照任务。快照用于后续历史恢复/审计，不取代 `document` 当前状态的事实来源。

Elasticsearch 的 `collab_documents` 索引是可重建副本，只索引标题和 Delta 的文本插入，不索引图片地址。新建、改名、删除在 MySQL 事务提交后更新索引；协同编辑通过 RabbitMQ 操作通知更新，周期巡检补建漏更新项。搜索前必须先从 MySQL 获取当前用户可见的文档 ID，再以 ES `ids` 条件限制结果，不能把 ES 中的字段当成权限来源。
