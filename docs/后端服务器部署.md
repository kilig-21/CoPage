# CoPage 后端服务器部署准备

部署位置、域名和费用由项目负责人确定。本文的配置已在本机临时环境验证，公网 TLS、域名、备份恢复演练仍需在选定服务器上完成。

## 独立启动配置

服务器使用根目录的 `compose.production.yml`，不要与本地开发的 `docker-compose.yml` 合并。项目名为 `copage-production`，数据卷与开发环境分开；数据库名固定为 `collab_doc`，应用使用 `copage` 数据库账号。

复制 `.env.production.example` 为 `.env.production`，在服务器本地填写各项值。密码和 JWT 密钥分别生成，推荐 32 字节随机 hex；root 密码和应用数据库密码应不同。前端来源填写完整的 HTTPS origin，不含路径或末尾 `/`；图片来源填写实际的 HTTPS 图片域名。真实凭据文件被 Git 忽略，勿通过聊天或提交记录传递。

Compose 对每项必要配置使用必填插值，空值会直接拒绝运行。执行配置检查时使用 `--quiet`，避免把解析后的凭据输出到日志；相关行为见 [Docker 插值文档](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/)。

```sh
docker compose --env-file .env.production -f compose.production.yml config --quiet
docker compose --env-file .env.production -f compose.production.yml up -d --build
docker compose --env-file .env.production -f compose.production.yml ps -a
```

MySQL 首次初始化只执行 `schema.sql`，不会创建 `testA/testB`。开发配置另外挂载 `demo-users.sql`；已有开发数据卷不需要重新初始化。不要把含演示账号的开发数据库卷直接当作正式环境使用，也不要用删除数据卷的方式重新执行初始化。

Redis 在该配置中启用密码，`prod` profile 通过 `REDIS_PASSWORD` 连接。MySQL、Redis、RabbitMQ、ES 和 MinIO 控制台不发布宿主机端口；后端与 MinIO 对象接口分别只绑定 `127.0.0.1:18080`、`127.0.0.1:19000`，可通过环境文件调整。ES 目前只在此项目的容器网络内提供无认证 HTTP，因此此模板适用于独立、可信的单机容器网络，不应将 ES 接入其他不可信项目的共享网络。

## HTTPS 入口

服务器上的反向代理需要提供两个 HTTPS 入口：

| 入口 | 上游 | 要求 |
| --- | --- | --- |
| 后端 API 与 WS | `127.0.0.1:18080` | 保留 `/api/` 路径；允许 11 MiB 请求；`/ws/collab` 转发 WebSocket Upgrade，空闲超时覆盖客户端心跳周期 |
| 图片公开 URL | `127.0.0.1:19000` | 保留 `/collab/对象key` 路径；公网入口仅开放 GET/HEAD，上传仍走鉴权后的后端 API |

MinIO 桶中的图片是公共读，不承载需要文档权限保护的私密附件。控制台和管理写入接口不交给图片公网入口。后端日志和代理日志避免记录 `/ws/collab?token=...` 的完整 query。

域名和证书配置好后，逐项验证真实 HTTPS/WSS、图片读取、双账号协同、断线恢复及刷新保留。前端部署到 Vercel 时，再按 README 设置 `VITE_BACKEND_HTTP_ORIGIN`、`VITE_BACKEND_WS_ORIGIN`；后端 `PROD_FRONTEND_ORIGIN` 必须与实际前端来源一致。

## 持久化与备份

MySQL 保存账号、文档、版本、操作日志和收据；MinIO 保存图片文件。这两项需要一起备份。Redis 是热状态，ES 是检索副本，RabbitMQ 是可重试通知；不能用这些副本代替 MySQL 或图片备份。

先安排维护窗口停止后端写入；在服务器受限目录保存数据库逻辑备份，再停止 MinIO，对它的数据卷做只读归档。示例在 Linux 服务器执行，`copage-production` 必须就是待备份的项目：

```sh
set -eu
umask 077
backup_dir="./backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
docker compose --env-file .env.production -f compose.production.yml stop backend
docker compose --env-file .env.production -f compose.production.yml exec -T mysql sh -ec \
  'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysqldump -uroot --single-transaction --routines --events --triggers collab_doc' \
  > "$backup_dir/mysql.sql"
docker compose --env-file .env.production -f compose.production.yml stop minio
minio_container=$(docker compose --env-file .env.production -f compose.production.yml ps -a -q minio)
test -n "$minio_container"
test "$(docker inspect --format '{{index .Config.Labels "com.docker.compose.project"}}' "$minio_container")" = copage-production
docker run --rm --network none --volumes-from "$minio_container:ro" redis:7.4.1-alpine \
  sh -ec 'tar -czf - -C /data .' > "$backup_dir/minio-data.tar.gz"
test -s "$backup_dir/mysql.sql"
test -s "$backup_dir/minio-data.tar.gz"
docker compose --env-file .env.production -f compose.production.yml start minio backend
```

如果备份失败，先保留错误与已有文件，再明确恢复被暂停的服务；不要继续使用不完整备份。将成功的备份加密复制到服务器之外，单独保管部署凭据。数据卷独立于容器存在，但 `down --volumes` 会删除卷；备份原理参考 [Docker 数据卷备份文档](https://docs.docker.com/engine/storage/volumes/#back-up-restore-or-migrate-data-volumes)。

上线前由负责人在选定服务器的独立项目和新数据卷中做一次恢复演练，核对正文、revision、操作历史、权限、登录与图片 URL；不要直接覆盖运行中的数据库。SQL 导出和图片卷归档/恢复路径已在本机合成数据上验证；真实服务器的备份与恢复演练尚未完成。

## 可重复的本机验证

```powershell
# 仅解析配置，不启动容器；随机测试凭据不会写入环境文件。
node scripts/production-compose-check.mjs
# 仅创建临时 MySQL/Redis，验证生产建表、账号权限、Redis 认证及开发种子。
node scripts/production-compose-check.mjs --smoke
# 创建完整临时环境及两个 prod 后端，注册临时账号并跑跨实例烟测。
node scripts/production-compose-check.mjs --full-smoke
# 在完整临时环境生成 SQL/图片卷备份，恢复到另一个全新项目，再核对恢复结果。
node scripts/production-compose-check.mjs --recovery-smoke
```

烟测使用随机项目名、独立数据卷与动态回环端口，结束前核对资源归属并清理自己的临时环境。2026-09-30 数据库/Redis 与完整环境烟测均通过：全新库没有演示账号，应用账号无法读取 MySQL 系统账号表，Redis 拒绝无密码请求；两个 `prod` 后端完成跨实例广播、已提交/未提交操作追赶、opId 去重和 30/30 并发 ack，最终 revision=34。临时容器、网络和卷均已清理。此项证明服务器模板的本机运行路径，公网入口和实际服务器恢复仍待验收。

恢复烟测会创建合成账号、带图片的文档及 20 次编辑，等待 revision=20 的快照，再停止写入并在系统临时目录生成 SQL 和图片卷归档。源项目停机后，将备份导入另一个空数据库和空 MinIO 卷。恢复目标的 Redis、MQ、ES 都是新卷；脚本核对登录、正文/revision、操作历史、幂等收据、快照、图片 SHA-256、只读协作者与无权限账号的访问边界，再通过冷 Redis 的历史追赶、重复 opId 去重和新操作提交验证可继续编辑。2026-09-30 完整验证通过：备份时 revision=20，恢复后原操作去重未改变版本，新操作将版本推进到 21；只读提交和无权访问均返回 403。通过后清理两个临时项目及合成备份；失败时保留合成备份路径供排查。它不会读取或备份你的开发数据库。

同日补验恢复后的搜索：先启动目标基础服务，确认 ES 业务索引不存在（HTTP 404），再启动后端；在没有新编辑或索引通知的情况下，定时重建从恢复的 MySQL 找回标题和正文。所有者及只读协作者均得到唯一目标文档，无权账号的命中数量为 0 且摘要列表为空。此项验证本机空索引重建及搜索权限，不代替真实公网验收。
